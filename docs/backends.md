# Backend support and capabilities

Query the declarations with `boxery host backends --json` (or `boxery-host backends --json`; `boxery backends` is the older spelling).
Query the **selected host's** configuration and local requirements with
`boxery host capabilities --json`. Agents use `vm_info {action:"capabilities"}` in both
MCP and pi. These discovery handlers run on the selected **host**, over SSH when it is remote; they do not start a backend, contact its provider or change backend configuration. The controller may still refresh its SSH configuration, feature-cache files or control connections. Read-only discovery is not an offline guarantee.
Use `boxery host capabilities --check` for setup preflight (nonzero on unsupported
configurations or missing locally checkable setup requirements).

## Platforms and validation

These platforms refer to the machine running **boxery-host**, not the controller.
A macOS controller can manage libvirt on a remote Linux host. exe.dev and boat.dev
run compute remotely, but their Boxery tunnels and services still run on the host.
Node platform/architecture names are used (`darwin`, `linux`, `x64`, `arm64`).
libvirt currently downloads an amd64 image, so its adapter is x64-only even though
upstream libvirt supports more architectures.

Supported means the adapter is intended to work; tested means an exact host/runtime
combination has recorded Boxery validation. Neither implies the other. Unrecorded
combinations warn during setup; unsupported ones fail before backend setup changes.
The table is generated by `metadataTable()` in `backends/index.mjs` and
checked by `test/backend-capabilities.test.mjs`.

“Not recorded” does not mean no provider testing occurred. The existing boat
live-test reports do not specify a complete host OS/architecture/runtime tuple;
they are not promoted into architecture-wide validation. exe's live runs recorded
macOS arm64 and Linux arm64 hosts; x64 hosts remain supported but untested. Cloud Hypervisor's recorded
validation used v54 on arm64 with nested KVM; x64 remains supported but untested.
See [backend implementation notes](../host/backends/README.md) for detailed live-test
coverage and image behavior. `fake` is internal test infrastructure, not a user backend.

OpenShell supports Apple Silicon macOS through Docker Desktop, but Boxery validation
is Linux/x64 with Docker and OpenShell 0.1.7. A gateway may be local or remote; the
read-only assessment does not infer its compute driver from the host OS. Its default
runtime is `gateway` (unknown driver), so the report remains untested until an exact
runtime is supplied to the shared evaluator. Restricted workloads have no sudo,
Boxery grants, desktop, disk image operations, resizing, pools or leases. Use
OpenShell providers for credentials. See [OpenShell setup](openshell.md).

## Contract (schemaVersion 1)

`backends --json` returns `{schemaVersion, backends:[...]}`. Each declaration contains:

- `id`, `stability`, `supported` host OS/architecture pairs and `tested` host/runtime tuples.
- `runtime`: local/remote location, default, options, and optional per-runtime platform restrictions.
- `requirements`: ID, tool/device/manual kind, actionable description, `setup` flag, and optional host platform condition.
- `capabilities`: desktop and headless creation, diskSnapshots, fork, restore, resize,
  pools, leases, guestSudo and grants. Each has a supported/conditional/unsupported
  `status`, prerequisite IDs in `requires`, and a `note` for limitations.

`capabilities --json` returns `{schemaVersion, backend, configuration, platform,
requirements, capabilities}`. `backend` is the same declaration; `configuration`
identifies this host and runtime, and `platform` separates supported and tested.
Requirements are met/missing/unknown/not-applicable. Evaluated capabilities have
available/unavailable/unknown `availability`, plus missing and unknown prerequisite IDs.

Availability describes adapter features, not general operational readiness: callers
must also inspect platform and requirements. For example, a supported feature can
still require installing a missing CLI. Manual requirements (accounts, privileges,
versions, billing entitlements) stay **unknown**, never assumed satisfied merely
because a token exists. Setup prints their instructions before invoking the backend's
more detailed authoritative checks. Queries do not authenticate with providers.

Boat's saved-snapshot access gates desktop creation, disk snapshots, forks, restore
and pools/leases. The free trial cannot satisfy it; unknown access is advisory until
the provider verifies it. Headless creation is explicitly unsupported and fails
before journals, VM creation, or provider calls. Snapshots are disk images, not RAM
checkpoints. Resize can restart a VM and only grows disks.

## Adding or changing a backend

Add its declaration to `backends/index.mjs`, including prerequisites and
conditional features rather than optimistic booleans. Record only verified test
combinations. Update the generated table here; tests enforce that every public shell
backend is declared and that this table matches the declarations. Keep backend
runtime validation for version-, privilege- and provider-specific failures.

A backend without a declaration (an out-of-tree `.sh` file) still runs: boxery-host
skips its preflight and operation checks, and `capabilities` reports it as undeclared.
